# Performance

Living document. Source of truth: `examples/auction/scripts/bench-bundle.ts`, `bench-loop.ts`,
`bench-browser.ts`, `bench-server.ts`, the bench pages and floors under `scripts/bench/`, and the code
named in each section.

This page records what µFW costs and where the cost comes from. Performance is not what µFW is for:
the reasons to use it are flexibility (one definition, several placements), correctness (a schema at every
cut point, every step recorded) and maintainability. Those reasons cost bytes and CPU, and this page
says how much, next to a plain baseline wherever one was measured. It is a
tradeoff, published as one.

Every figure is regenerated by one of these commands (each needs `pnpm install`; `bench:browser` also
needs Chromium, installed once with `pnpm exec playwright install chromium`):

| Command | Produces |
|---|---|
| `pnpm --filter @mufw/example-auction bench:bundle` | [Bundle](#bundle) |
| `pnpm --filter @mufw/example-auction bench:browser` | [Startup in the browser](#startup-in-the-browser) and [Interaction](#interaction), at CPU throttling 1× and 4× |
| `BENCH_CPU_RATES=6,10 pnpm --filter @mufw/example-auction bench:browser` | the 6× and 10× rows |
| `pnpm --filter @mufw/example-auction bench:loop` | [The loop in Node](#the-loop-in-node) |
| `pnpm --filter @mufw/example-auction bench:server` | [Server](#server) |

The figures come from one run of each script on an Apple M5 (10 CPUs, 16.0 GiB), Node 24.21.0, headless
Chromium 156.0.8078.4 and localhost. A figure moves with the machine and with what else it runs; rerun
the scripts when a change moves a cost, and do not quote a figure from this page as a constant. Each
script's header comment lists what it does not measure; the biases that matter are repeated in the
section that uses them.

Units. Bundle sizes are KiB (1024 bytes), as `bench:bundle` prints them. External figures keep their
own unit: bundlejs and the Effect posts use kB (1000 bytes), and the tables that mix the two say so.
"Derived" marks arithmetic on printed figures; "inference" marks a statement no script measured.

## Bundle

minified JavaScript raw, gzip at level 9 and brotli at quality 11. These are best-case compressions;

## Interaction

Click to DOM runs from the click event's own timestamp to the mutation that shows the update. Click to
next frame runs from the same start to `requestAnimationFrame` then `setTimeout(0)`, the usual proxy for
what Interaction to Next Paint measures. Medians, ms:

| Page | Click to DOM, 1× | 4× | 10× | Click to next frame, 1× | 4× | 10× |
|---|---|---|---|---|---|---|
| `counter-uhtml` | 0.3 | 0.8 | 2.2 | 15.3 | 14.9 | 13.0 |
| `counter-mufw` | 0.5 | 1.1 | 2.8 | 15.2 | 15.2 | 12.9 |
| `list-uhtml` | 0.8 | 2.0 | 5.2 | 17.1 | 17.8 | 21.3 |
| `list-mufw` | 0.9 | 2.4 | 6.2 | 16.7 | 17.7 | 21.3 |
| auction | 0.7 | 1.7 | 4.7 | 16.1 | 16.1 | 16.4 |

A µFW page shows a click's result in the click's own task: click to DOM is within 0.1 to 1.0 ms of the
baseline's in every row (derived), and click to next frame is 0.98× to 1.02× the baseline's at every rate
(ratios as printed by `bench:browser`, counter and list, 1× to 10×).

### The input scheduler

The click reaches the render through two fiber hops: the `IntentBus` queue offer that wakes the
actions-drain fiber (`packages/core/src/Layers.ts`), and `Effect.forkScoped` of the present. Effect's
default `MixedScheduler` posts each hop as a macrotask, `setTimeout(0)` in browsers
(`node_modules/effect/dist/Scheduler.js`), and Chromium holds a macrotask posted from a real input event
until the next frame. Probed with throwaway pages (not a committed script), the default scheduler showed
about 16 ms click to DOM headless and about 7.4 ms headed on a 120 Hz display. It is not the
nested-`setTimeout` 4 ms clamp: a `MessageChannel` scheduler gave the same 15.9 ms. A synthetic
`button.click()` from script does not show the delay; real input does.

`layerInputScheduler` (`packages/view-uhtml/src/Scheduler.ts`) is a `MixedScheduler("async", defer)` whose
deferred tasks run as microtasks, in the task of the click, so the hops and the render finish before the
browser looks for the next frame. A pure microtask scheduler (`new MixedScheduler("sync")`) would remove
the frame as well, but it never yields to the event loop: a fiber that does heavy CPU work could starve
input and rendering. So the scheduler keeps a budget: while the time spent in deferred tasks since the
last reset is under `inputBudgetMillis` (5 ms), a task runs as a microtask; beyond it, as
`setTimeout(0)`. The first deferral of a window posts a reset, also a `setTimeout(0)`, which zeroes the
time spent. The budget counts the time the tasks take, not elapsed time, so a page that sits idle between
clicks has a full budget for each. One click's hops cost well under a millisecond, so they fit; a fiber
that keeps working hands control back after 5 ms and leaves most of a 16.7 ms frame to input and paint.

Each browser page root provides it with `Layer.provide`, last, around the whole page: the `IntentBus`
queue keeps the dispatcher of the fiber that built it, so a layer built beneath the scheduler would keep
the default. The web worker and the server keep the default scheduler.

An update that does not start from input was never held: the ticker island of `compare:transports`,
which renders a server push through the remote `ModelPort` and `layerMountReadOnly`, shows an update in
0.5 ms median over the websocket and 0.7 ms over HTTP. [Those two figures come from that script, not from
the commands of this page.]

### What it means for INP

Interaction to Next Paint [is good at or below 200 ms](https://web.dev/articles/inp) at the 75th percentile.
Across the table, and the 6× rows of the same run, click to next frame is at most 21.3 ms median (the
`list-mufw` and `list-uhtml` rows at 10×) and its p95 at most 25.6 ms (`list-mufw` at 10×), 13% of the
threshold (derived: 25.6 / 200). The benchmark's proxy is not the field metric, and a real page's handlers
and long tasks add to it. A click whose fibers work for more than the 5 ms budget moves its remaining hops
to macrotasks, which Chromium holds until the next frame [inference: the benchmark's clicks stay far under
the budget].

### Constant wait and growing work

What remains of the click to DOM is work, and it grows with throttling in the baseline too:
`counter-mufw` rises from 0.5 ms at 1× to 2.8 ms at 10× and `counter-uhtml` from 0.3 to 2.2; `list-mufw`
from 0.9 to 6.2 ms (+5.3) and `list-uhtml` from 0.8 to 5.2 ms (+4.4). The gap between µFW and uhtml is
0.2, 0.3 and 0.6 ms at 1×, 4× and 10× for the counter and 0.1, 0.4 and 1.0 ms for the list (derived): the
step, which slows down under throttling like the render. The render itself is uhtml's work. On
[js-framework-benchmark](https://krausest.github.io/js-framework-benchmark/2026/chrome154.html)
(Apple M4, Chrome 154, a 1000-row table) uhtml 5.0.3, a newer major version than the 4.x µFW uses, has
a geometric mean of 1.180 against vanilla JavaScript, 64th of 196 keyed implementations (derived from the
published results, not the site's own ranking).

## The loop in Node

`bench:loop` runs the loop in one Node process on a warm JIT, with `AutoActions` false: the least a step
costs, not a first-interaction time. Three definitions: the bench `Counter` (the smallest step), the
bench `List` (1000 rows) and the example's `Auction`. "Plain" is the definition's pure functions called
in a JavaScript loop, with no loop, schemas, history or ports.

### One step

Median µs per step; the ratio is the cost relative to the plain reducer:

| Definition | plain | `applyProposal` | `ModelPort.present` | `IntentPort.dispatch` until its record |
|---|---|---|---|---|
| Counter | 0.007 | 0.018 (2.1×) | 2.875 (399×) | 34.00 (3951×) |
| List (1000 rows) | 4.305 | 2.672 (0.6×) | 11.25 (3.0×) | 41.62 (9.8×) |
| Auction | 0.754 | 0.472 (0.6×) | 4.541 (7.4×) | 36.46 (48.2×) |

`present` throughput as printed: 283,648 steps/s for the Counter, 74,580 for the List, 172,084 for the
Auction; `dispatch` to its record: 28,646, 22,399 and 26,290 per second.

The loop adds about 3 to 7 µs per step (derived: `present` minus plain, 2.9 µs for the Counter, 6.9 µs
for the List, 3.8 µs for the Auction) and about 30 to 32 µs for an intent round trip (derived: `dispatch`
minus `present`, 31.1, 30.4 and 31.9 µs). Every commit also estimates the retained size of its record
(`footprint` in `packages/core/src/Footprint.ts`), and the `present` figures include it. The walk visits
every slot of each array the step copied and each node the step replaced, and nothing the step left alone:
for the List it is the 1000 slots of the copied row array, for the Counter a model and representation of a
few slots. No case isolates the estimate, so its share of the figures above is not measured. The ratio is
large for a counter because the plain step is a handful of instructions, and it fades as the domain does
real work: 3.0× at 1000 rows. A step that costs microseconds in the domain does not notice the loop. A
step that is a single addition does.

### History memory

`HistoryLimit` (default 1000) bounds the number of records and `HistoryRetainedSize` (default 64 MiB of
estimated bytes; `Infinity` disables it) bounds their estimated size. Each record holds its own model.
After each commit the oldest records after seq 0 are evicted while the count exceeds `HistoryLimit` or the
sum of the estimates exceeds the bound; seq 0 and the newest record are always kept. A record costs what
its model and representation keep alive beyond its predecessor's (`footprint`): a node `===` to the
predecessor's at the same path costs 0, an array or object 16 bytes plus 8 per slot or key, a string that
changed its length. It is an estimate, not a heap measure: evicting a record can leave its successor
holding parts it was counted as sharing with it, so the retained heap can exceed the bound.

Heap kept per retained record, after garbage collection, with `HistoryLimit` 1000 and the size bound not
reached:

| Definition | Bytes per record, 1000 steps / 2000 steps |
|---|---|
| Counter | 237 / 249 |
| List (1000 rows) | 8338 / 8377 |

The List's record is the new 1000-pointer array of each step, the rows being shared between records: 8134.5
KiB grown over 1000 records. Copying the rows one by one would cost 48.4 KiB per record. The 1000 List
records weigh about 8 MiB (derived: 8134.5 KiB), well under the 64 MiB default, so there the count binds.
The size bound binds for a model whose collections grow: the Auction after its opening and N bids, heap
after garbage collection, with the default bound and with `Infinity` (count only; see also
[Server memory](#memory)):

| Bids | `HistoryRetainedSize` | Records kept | Heap before MiB | Heap after MiB | Grown MiB | KiB per record |
|---|---|---|---|---|---|---|
| 5000 | 64.0 MiB | 919 | 49.2 | 97.8 | 48.7 | 54.2 |
| 5000 | `Infinity` | 1000 | 49.2 | 101.6 | 52.4 | 53.7 |
| 20000 | 64.0 MiB | 211 | 49.3 | 98.6 | 49.3 | 239.4 |
| 20000 | `Infinity` | 1000 | 49.3 | 274.2 | 224.9 | 230.3 |

With the size bound the retained heap stays near 49 MiB as the model grows from 5000 to 20000 bids (211
records kept at the end), while the count-only history grows to 224.9 MiB. The bound is 64.0 MiB of
estimated bytes and the measured heap grown is about 49 MiB: the estimate is approximate, and here it
is above the heap.

|---|---|---|
| `Effect.runSync(Effect.succeed(1))` | 14.01 | 4.0× |
| `yield* Effect.succeed(1)` inside a program | 38.75 | 11.0× |
| `Effect.runSync(Effect.gen, 3 yields)` | 706.3 | 199× |
| `yield* Effect.gen, 3 yields` inside a program | 576.6 | 163× |

Effect's own documentation [acknowledges](https://effect.website/docs/v3/additional-resources/myths) that
a micro-operation costs far more than the primitive it replaces and argues it is irrelevant at
application level. The 4.0 release post claims 4.57M tasks per second and about 0.44 KB per fiber,
self-reported with no plain-promise baseline; none was found elsewhere.

## Server

`bench:server` starts `src/server.ts` as a child process (through `tsx`, not a production build, automatic
actions off, a fresh auction per row) and drives it from another Node process over the real remote
adapters: `Rpc.layerClient` on a JSON websocket, localhost, no TLS. The load is closed-loop: a connection
sends when its last request is answered. The load generator shares the CPUs and is one thread; its
CPU is in the tables, and about 100% means the generator limits the row. The auction's `bids` array
grows with every accepted bid, so a step costs more late in a run than early (the last fifth of
samples is 2.5× to 4.0× the first fifth's median latency in the `Present` rows). Each step also copies the
`bids` array, and the history record's size estimate walks its slots [as read from the code; no measurement
isolates the walk].

### `Present`

| Connections | Steps/s | p50 ms | p95 ms | p99 ms | Server CPU % mean | Generator CPU % |
|---|---|---|---|---|---|---|
| 1 | 5926 | 0.14 | 0.23 | 0.64 | 114 | 21 |
| 1 (the same row measured again in table 2 of the script) | 5943 | 0.14 | 0.24 | 0.47 | 117 | 19 |
| 10 | 7701 | 1.03 | 3.00 | 6.60 | 134 | 21 |
| 50 | 6287 | 7.10 | 16.92 | 34.50 | 131 | 23 |
| 200 | 6684 | 29.59 | 58.50 | 65.63 | 137 | 24 |

A connection sending steps one after the other is served at 5926 to 5943 steps/s with a median of 0.14 ms.
More connections raise the total to at most 7701 steps/s (10 connections; 6287 and 6684 at 50 and 200)
while latency grows with them: one definition is one serialised writer, so connections queue for the permit
(the in-process [concurrent presenters](#concurrent-presenters-subscribers-boundary) show the same flat
line).

### `Submit`

The server runs the action behind the authentication middleware and answers when the intent is queued, so
the latency is the acknowledgement; applied steps are read from `History`.

| Connections | Acks/s | Ack p50 ms | Ack p99 ms | Applied steps/s | Accepted / rejected | Catch-up after the load s |
|---|---|---|---|---|---|---|
| 1 | 18620 | 0.05 | 0.13 | 17560 | 199 / 93102 | 0.3 |
| 50 | 32545 | 1.39 | 3.65 | 30962 | 175 / 162781 | 0.3 |

Nearly every bid is rejected after the credit limit, a `BidRejected` proposal that is a cheap step and
does not grow the model. These rates are therefore for cheap steps; the `Present` rows, which accept every
bid, are the ones that show what a growing model does.

### Fan-out

S websocket subscribers to `Representations`, one `Present` every 20 ms for 5 s (250 updates, all
delivered to all subscribers in every row). Each representation carries every bid so far. Delay is from
sending an update to the moment the last subscriber has it:

| Subscribers | Delay p50 ms | p95 ms | max ms | Server CPU % mean / max | Server RSS MiB mean / max | Generator CPU % |
|---|---|---|---|---|---|---|
| 1 | 1.36 | 2.19 | 3.39 | 7 / 12 | 200.3 / 200.6 | 4 |
| 100 | 6.93 | 11.80 | 21.64 | 36 / 52 | 245.0 / 260.6 | 42 |
| 500 | 72.26 | 120.51 | 211.36 | 91 / 112 | 335.2 / 384.3 | 111 |
| 1000 | 138.66 | 226.74 | 328.74 | 92 / 153 | 378.1 / 436.0 | 119 |

The 500 and 1000 rows are partly the load generator's: it is above 100% there, and the subscribers it
runs are one thread. The server CPU at 1000 subscribers is 92% of one core on average, which is
50,000 deliveries per second (50 updates/s times 1000), about 18 µs of server CPU per delivery (derived).
That is the order of one JSON encoding of a 2.2 KiB representation (13.35 µs median in `bench:loop`),
which fits the design below; no script isolates the encoding from the framing and the send, so this is an
inference, not a measurement. The representations here grow to the size of the bids the run has made;
their final byte size is not printed.

The cost is structural: each `Representations` subscriber is its own stream (the handler in
`packages/rpc/src/index.ts` reads `model.representations` through a sliding buffer of
`RepresentationBacklog`), the representation is the whole view and not a difference, and the server
encodes it once per subscriber [as read from the code, not isolated by a measurement].

### Memory

Server RSS and V8 heap in use, with no garbage collection forced, as one client sends bids:

| Moment | Steps sent | RSS MiB | RSS above idle MiB | Heap used MiB |
|---|---|---|---|---|
| idle after start | 0 | 198.8 | 0.0 | 50.9 |
| after 1000 steps | 1000 | 228.3 | 29.5 | 100.8 |
| after 5000 steps | 5000 | 381.9 | 183.1 | 222.9 |
| 1 s later, idle | 5000 | 381.9 | 183.1 | 222.9 |

During the 5 second `Present` windows RSS means 691.0 to 1101.8 MiB and peaks between 1016.7 and 1485.1
MiB over 1 to 200 connections (29,832 to 38,718 bids sent per window). No garbage collection is forced in
these windows, so RSS includes garbage: every accepted bid copies the model's `bids` array, a 30,000-slot
array near the end of a window, about 233 KiB at 8 bytes per slot (derived from 29,832 bids; the slot size
is an inference). Over the window the copies add up to about 3.3 GiB of allocation (derived: the sum over
steps of slots times 8 bytes), which the collector frees on its own schedule, so RSS follows the collector
and not what the model keeps. What the history retains is bounded by `HistoryLimit` and by
`HistoryRetainedSize`; the auction rows of [History memory](#history-memory) are the measurement: with the
bound the retained heap is 49.3 MiB at 20,000 bids, by count only 224.9 MiB. The model
itself still grows with every accepted bid. The `Submit` windows, where the model stops growing at the
credit limit, stay at 378.2 and 414.8 MiB mean.

### Synchronisation

`Present` from one client, 2000 timed bids on a fresh set of processes per row (200 bids already in the
model), with `MUFW_SYNC`:

| Client talks to | Steps/s | p50 ms | p95 ms | p99 ms | p50 vs no sync |
|---|---|---|---|---|---|
| a server without sync | 12475 | 0.07 | 0.11 | 0.26 | 1.00× |
| the host of the log | 6051 | 0.13 | 0.30 | 0.68 | 1.94× |
| a joiner of the log | 2778 | 0.32 | 0.52 | 1.12 | 4.68× |

Sync adds 0.06 ms at the host and 0.25 ms at a joiner (derived), on one machine over loopback. A joiner's `present`
appends to the log held by the host and returns once the entry is applied, so on a real network each
proposal at a joiner adds the round trip to the host [inference from the layer's contract in
[the SAM loop](sam-loop.md#synchronisation-across-instances); loopback hides it].

## Where the costs come from

Each cost is the price of a design choice, in the order of the sections above:

| Choice | What it buys | What it costs |
|---|---|---|
| The runtime is Effect, and every cut point is a `Schema` | typed errors and services, layers for placement, scoped fibers, parsing at the boundary | 7.1 KiB gzip for the runtime, 22.4 with schemas, 32.0 with streams and layers (the [floors](#floors)); script time at load; 0.1 µs to decode an intent and about 92 µs for a 21 KiB model |
| Every step is recorded as a history record | time travel, replay, model-based path tests, the history stream of the devtools | 237 bytes per record (Counter), 8377 (List), 239.4 KiB (Auction at 20,000 bids); a bound on count and on estimated size (`HistoryLimit`, `HistoryRetainedSize`); each commit walks the slots of the arrays the step copied to estimate the record's size |
| A representation is the whole view, not a diff | a subscriber that falls behind skips to the newest snapshot and loses nothing; no diff protocol | the whole representation is encoded and sent per update; fan-out cost grows with its size |
| One serialised writer per definition | every step atomic, in order, one permit | steps/s does not grow with connections; latency does |
| Fiber hops between an intent and the render (queue, drain fiber, forked present) | the loop is the same code in every placement | nothing in frames under `layerInputScheduler`, which the browser page roots provide (0.5 ms click to DOM at 1×); the default scheduler of the worker and the server posts each hop as a macrotask, and an intent's round trip costs 30 to 32 µs more than `present` in Node |
| Each `Representations` subscriber is its own stream | per-client backpressure and a bounded buffer for a stalled client | the server encodes per subscriber |

## What this means realistically

µFW is not a performance-first framework. Its bundle, startup CPU and per-step cost are larger than a
view library's and a plain reducer's, and most of that is Effect, which it uses on purpose. What one gives
up is bytes, main-thread time at load, per-step time, and
per-subscriber server work. What one gets is the SAM definition as the single source of the domain, a
schema at every boundary, recorded steps, and the choice of placement per deployment without a domain
change.

Derived from the numbers above:

| Fits | Because |
|---|---|
| Forms, back-office screens, workflows, admin tools | click to next frame is 0.98× to 1.02× the baseline's at every rate and at most 25.6 ms p95 at 10× throttling; a step costs microseconds |
| Applications that load once and stay open | the 42.8 to 74.4 KiB gzip is paid once; 1.2 to 2.0 MiB of heap |
| Dashboards with some hundreds of viewers of one definition | 100 subscribers at 50 updates/s see p50 6.93 ms, p95 11.80 ms; the cost scales with updates times subscribers [inference] |
| A server with a few thousand proposals per second on one definition | `Present` over a websocket is 5926 to 7701 steps/s with a growing model, `Submit` applies 17560 to 30962 cheap steps/s |

| Does not fit without a change | Because |
|---|---|
| A page whose first-load JavaScript budget is tens of KiB | the framework floor is 42.8 KiB gzip (`counter-mufw`; the `mufw-core` floor is 38.1); `browser-only` is 74.4 |
| A 60 Hz animation driven through the loop | every intent costs 34.00 µs to its record in Node and adds a history record per step; the input scheduler's 5 ms budget under an animation load is not measured; drive animation outside the loop [inference] |
| Thousands of live viewers of one large representation in one server process | 500 subscribers at 50 updates/s see p50 72.26 ms and 1000 see 138.66 ms, near one core of server CPU; more than one server process is not measured |
| A single definition that must apply more than about 8,000 proposals per second | the `Present` ceiling measured is 7701 steps/s; one writer does not scale with connections |
| A model whose collections grow without bound | history is bounded, the model is not: with the size bound the retained heap stays near 49 MiB from 5000 to 20000 bids (224.9 MiB by count only), but each step copies the array and walks its slots, and the last fifth of a 5 second window is 2.5× to 4.0× the first fifth's median latency; RSS is 183.1 MiB above idle after 5000 bids and 691.0 to 1101.8 MiB mean in a 5 second window |
| A weak device with a strict first-interaction budget | 107.5 ms median first content for a counter and 252.1 ms for the auction at 10× throttling, compute alone; counter script time is 6.61× to 7.67× the baseline |

No performance gap is listed: the costs above are the design.
