# Performance

Living document. Source of truth: `examples/auction/scripts/bench-bundle.ts`, `bench-loop.ts`,
`bench-browser.ts`, `bench-server.ts`, the bench pages and floors under `scripts/bench/`, and the code
named in each section.

This page records what µFW costs and where the cost comes from. Performance is not what µFW is for:
the reasons to use it are flexibility (one definition, several placements), correctness (a schema at every
cut point, every step recorded) and maintainability. Those reasons cost bytes, CPU and one frame of
latency, and this page says how much, next to a plain baseline wherever one was measured. It is a
tradeoff, published as one.

Every figure is regenerated by one of these commands (each needs `pnpm install`; `bench:browser` also
needs Chromium, installed once with `pnpm exec playwright install chromium`):

| Command | Produces |
|---|---|
| `pnpm --filter @mufw/example-auction bench:bundle` | [Bundle](#bundle) |
| `pnpm --filter @mufw/example-auction bench:browser` | [Startup in the browser](#startup-in-the-browser) and [Interaction](#interaction), at CPU throttling 1× and 4× |
| `BENCH_CPU_RATES=6,10 pnpm --filter @mufw/example-auction bench:browser` | the 6× and 10× rows |
| `pnpm --filter @mufw/example-auction bench:loop` | [The loop in Node](#the-loop-in-node) |
| `pnpm --filter @mufw/example-auction bench:server` | [Server](#server) |

The figures come from one run of each script on an Apple M5 (10 CPUs, 16.0 GiB), Node 24.21.0, headless
Chromium 156.0.8078.4 and localhost. A figure moves with the machine and with what else it runs; rerun
the scripts when a change moves a cost, and do not quote a figure from this page as a constant. Each
script's header comment lists what it does not measure; the biases that matter are repeated in the
section that uses them.

Units. Bundle sizes are KiB (1024 bytes), as `bench:bundle` prints them. External figures keep their
own unit: bundlejs and the Effect posts use kB (1000 bytes), and the tables that mix the two say so.
"Derived" marks arithmetic on printed figures; "inference" marks a statement no script measured.

## Bundle

`bench:bundle` builds every entry in memory with vite 8 (minified, tree-shaken), then reports the
minified JavaScript raw, gzip at level 9 and brotli at quality 11. These are best-case compressions;
a server with a lower setting sends more. CSS, HTML and parse time are not in it.

### Against a budget

[Russell's 2026 budget](https://infrequently.org/2025/11/performance-inequality-gap-2026/) for a 3

Script time is where the extra 193 KiB of JavaScript shows: the browser parses, compiles and evaluates
it before the first content. First content is 2.3 to 3.2 times the baseline and not more because the
page's own rendering is common to both. Heap after load, median MiB: `counter-mufw` 1.4, `list-mufw` 1.8,
auction 2.1, against 0.7 for `counter-uhtml` and 1.1 for `list-uhtml`.

How far the rates reach. Russell puts mid-tier phones more than 3.5× and low-end phones about 9× slower
than current iPhones on single-core Geekbench 6, so 4× and 10× bracket them, approximately. The baseline
here is an M5, which is likely faster than an iPhone [inference], so the rates may understate a real
low-end phone. CPU throttling slows the main thread only; it does not model a phone's memory pressure,
storage or thermal limits. The loads are localhost with no compression, and the figures leave out the
network: the transfer time of the [budget table](#against-a-budget) is not added to them. At 10× the
auction's median first content is 307.2 ms of compute, against the 2.5 s the [Largest Contentful Paint
threshold](https://web.dev/articles/lcp) allows; what the network adds is not measured.

## Interaction

Click to DOM runs from the click event's own timestamp to the mutation that shows the update. Click to
next frame runs from the same start to `requestAnimationFrame` then `setTimeout(0)`, the usual proxy for
what Interaction to Next Paint measures. Medians, ms:

| Page | Click to DOM, 1× | 4× | 10× | Click to next frame, 1× | 4× | 10× |
|---|---|---|---|---|---|---|
| `counter-uhtml` | 0.2 | 0.8 | 2.3 | 15.6 | 15.1 | 13.1 |
| `counter-mufw` | 15.8 | 15.6 | 13.3 | 32.3 | 31.9 | 29.4 |
| `list-uhtml` | 0.6 | 2.1 | 6.8 | 16.6 | 17.5 | 26.8 |
| `list-mufw` | 17.1 | 18.8 | 23.6 | 33.6 | 35.2 | 39.8 |
| auction | 16.0 | 16.3 | 15.9 | 33.2 | 34.1 | 36.1 |

A µFW page shows a click's result about one frame after the click (click to DOM near 16 ms), and its next
frame comes about one frame later than the baseline's.

### The cause

Probed with throwaway pages (not a committed script). The click reaches the render through two fiber
hops: the `IntentBus` queue offer that wakes the actions-drain fiber (`packages/core/src/Layers.ts`), and
`Effect.forkScoped` of the present. Effect's default `MixedScheduler` posts each hop as a macrotask,
`setTimeout(0)` in browsers (`node_modules/effect/dist/Scheduler.js`), and Chromium holds a macrotask
posted from a real input event until the next frame. The probe measured about 16 ms headless and about
7.4 ms headed on a 120 Hz display. It is not the nested-`setTimeout` 4 ms clamp: a `MessageChannel`
scheduler gives the same 15.9 ms. A synthetic `button.click()` from script does not show the delay; real
input does.

An update that does not start from input is not held: the ticker island of `compare:transports`, which
renders a server push through the remote `ModelPort` and `layerMountReadOnly`, shows an update in 0.5 ms
median over the websocket and 0.7 ms over HTTP.

With a microtask scheduler (`Scheduler.Scheduler` from `effect/Scheduler`, `new MixedScheduler("sync")`
provided at the composition root) the probe's click to DOM falls to 0.3 ms, equal to plain uhtml. A
microtask scheduler never yields to the event loop, so a fiber that does heavy CPU work can starve input
and rendering. That is why it is not applied; the gap is listed in [TODO](../TODO.md#performance).

### What it means for INP

Interaction to Next Paint [is good at or below 200 ms](https://web.dev/articles/inp) at the 75th percentile.
The extra frame is about 16.7 ms on a 60 Hz display and 8.3 ms on a 120 Hz one (derived). Across the
table, click to next frame is at most 39.8 ms median (`list-mufw` at 10×) and its p95 at most 45.5 ms
(same row), 23% of the threshold (derived). The benchmark's proxy is not the field metric, and a real
page's handlers and long tasks add to it; the point is that the delay is visible in a benchmark that
compares frames and far inside the threshold.

### Constant wait and growing work

The delay is waiting, not CPU: `counter-mufw` click to DOM stays at 13.3 to 15.8 ms from 1× to 10×. The
list shows work: `list-mufw` rises from 17.1 to 23.6 ms (+6.5) and `list-uhtml` from 0.6 to 6.8 ms
(+6.2), so the gap between them stays at about one frame (16.5 ms at 1×, 16.8 ms at 10×, derived) and the
growth is the step and the render of a 1000-row list slowing down under throttling. The render itself
is uhtml's work. On [js-framework-benchmark](https://krausest.github.io/js-framework-benchmark/2026/chrome154.html)
(Apple M4, Chrome 154, a 1000-row table) uhtml 5.0.3, a newer major version than the 4.x µFW uses, has
a geometric mean of 1.180 against vanilla JavaScript, 64th of 196 keyed implementations (derived from the
published results, not the site's own ranking).

## The loop in Node

`bench:loop` runs the loop in one Node process on a warm JIT, with `AutoActions` false: the least a step
costs, not a first-interaction time. Three definitions: the bench `Counter` (the smallest step), the
bench `List` (1000 rows) and the example's `Auction`. "Plain" is the definition's pure functions called
in a JavaScript loop, with no loop, schemas, history or ports.

### One step

Median µs per step; the ratio is the cost relative to the plain reducer:

| Definition | plain | `applyProposal` | `ModelPort.present` | `IntentPort.dispatch` until its record |
|---|---|---|---|---|
| Counter | 0.007 | 0.017 (1.9×) | 2.333 (306×) | 31.08 (3517×) |
| List (1000 rows) | 4.306 | 2.662 (0.6×) | 7.000 (1.9×) | 36.37 (8.4×) |
| Auction | 0.736 | 0.463 (0.6×) | 2.792 (5.3×) | 34.29 (47.3×) |

`present` throughput as printed: 352,953 steps/s for the Counter, 112,137 for the List, 245,110 for the
Auction; `dispatch` to its record: 30,719, 25,599 and 27,415 per second.

The loop adds a fixed cost of about 2 to 3 µs per step (derived: `present` minus plain, 2.3 µs for the
Counter, 2.7 µs for the List, 2.1 µs for the Auction) and about 29 to 32 µs for an intent round trip
(derived: `dispatch` minus `present`). The ratio is large for a counter because the plain step is a
handful of instructions, and it fades as the domain does real work: 1.9× at 1000 rows. A step that costs
microseconds in the domain does not notice the loop. A step that is a single addition does.

### Concurrent presenters, subscribers, boundary

| K fibers calling `present` at once | steps/s | mean µs per call |
|---|---|---|
| 1 | 340,305 | 2.905 |
| 10 | 347,943 | 28.61 |
| 100 | 340,658 | 265.3 |

Throughput stays flat: one definition's model applies proposals under one permit, so more presenters add
latency, not throughput. This is the single writer that makes every step atomic and recorded in order.

| S subscribers to `representations` while presenting | mean µs per step, including one yield | ratio to none |
|---|---|---|
| 0 | 15.83 | 1.0× |
| 1 | 16.54 | 1.0× |
| 10 | 22.59 | 1.4× |
| 100 | 78.23 | 4.9× |

Each subscriber adds about 0.6 µs per step (derived: 100 subscribers, (78.23 − 15.83) / 100).

Schema decoding and JSON encoding at a cut point, median µs:

| Value | Decode | Model to JSON text | JSON text to model |
|---|---|---|---|
| Counter intent | 0.109 | | |
| Counter model | 0.075 | 0.140 | 0.165 |
| Auction model, 50 bids (2.2 KiB) | 6.820 | 12.40 | 14.54 |
| List model, 1000 rows (21.1 KiB) | 85.54 | 115.6 | 128.0 |

An intent or proposal decodes in 0.1 to 0.2 µs. A model or representation costs in proportion to its size:
about 90 µs to decode and about 120 µs to encode at 21 KiB. A remote placement pays this at each hop
that crosses the wire.

### History memory

`HistoryLimit` (default 1000) bounds the number of records, each holding its own model. Heap kept per
retained record, after garbage collection:

| Definition | Bytes per record, 1000 steps / 2000 steps |
|---|---|
| Counter | 218 / 225 |
| List (1000 rows) | 8328 / 8367 |

The List's record is the new 1000-pointer array of each step, the rows being shared between records: 8124.6
KiB grown over 1000 records. Copying the rows one by one would cost 55.5 KiB per record. The bound is on
count, not size; see [Server memory](#memory) and [TODO](../TODO.md#performance).

### Effect on its own

Mean ns per operation, as context for the 2 to 3 µs:

| Operation | ns | vs a plain call (2.925 ns) |
|---|---|---|
| `Effect.runSync(Effect.succeed(1))` | 11.99 | 3.9× |
| `yield* Effect.succeed(1)` inside a program | 35.92 | 11.6× |
| `Effect.runSync(Effect.gen, 3 yields)` | 609.8 | 196× |
| `yield* Effect.gen, 3 yields` inside a program | 518.7 | 166× |

Effect's own documentation [acknowledges](https://effect.website/docs/v3/additional-resources/myths) that

application level. The 4.0 release post claims 4.57M tasks per second and about 0.44 KB per fiber,
self-reported with no plain-promise baseline; none was found elsewhere.

## Server

`bench:server` starts `src/server.ts` as a child process (through `tsx`, not a production build, automatic
actions off, a fresh auction per row) and drives it from another Node process over the real remote
adapters: `Rpc.layerClient` on a JSON websocket, localhost, no TLS. The load is closed-loop: a connection
sends when its last request is answered. The load generator shares the CPUs and is one thread; its
CPU is in the tables, and about 100% means the generator limits the row. The auction's `bids` array
grows with every accepted bid, so a step costs more late in a run than early (the last fifth of
samples is 1.8× to 3.4× the first fifth's median latency in the `Present` rows).

### `Present`

| Connections | Steps/s | p50 ms | p95 ms | p99 ms | Server CPU % mean | Generator CPU % |
|---|---|---|---|---|---|---|
| 1 | 7305 | 0.10 | 0.19 | 0.49 | 117 | 27 |
| 1 (the same row measured again in table 2 of the script) | 7823 | 0.10 | 0.15 | 0.46 | 120 | 25 |
| 10 | 10710 | 0.63 | 1.98 | 8.54 | 151 | 28 |
| 50 | 9331 | 4.21 | 13.47 | 26.12 | 151 | 32 |
| 200 | 9290 | 18.59 | 49.17 | 91.97 | 153 | 29 |

A connection sending steps one after the other is served at 7305 to 7823 steps/s with a median of 0.10 ms.
More connections raise the total to 9290 to 10710 steps/s and no further, while latency grows with them:
one definition is one serialised writer, so connections queue for the permit (the in-process
[concurrent presenters](#concurrent-presenters-subscribers-boundary) show the same flat line).

### `Submit`

The server runs the action behind the authentication middleware and answers when the intent is queued, so
the latency is the acknowledgement; applied steps are read from `History`.

| Connections | Acks/s | Ack p50 ms | Ack p99 ms | Applied steps/s | Accepted / rejected | Catch-up after the load s |
|---|---|---|---|---|---|---|
| 1 | 18298 | 0.05 | 0.11 | 17292 | 199 / 91493 | 0.3 |
| 50 | 36950 | 1.20 | 3.44 | 34897 | 199 / 184795 | 0.3 |

Nearly every bid is rejected after the credit limit, a `BidRejected` proposal that is a cheap step and
does not grow the model. These rates are therefore for cheap steps; the `Present` rows, which accept every
bid, are the ones that show what a growing model does.

### Fan-out

S websocket subscribers to `Representations`, one `Present` every 20 ms for 5 s (250 updates, all
delivered to all subscribers in every row). Each representation carries every bid so far. Delay is from
sending an update to the moment the last subscriber has it:

| Subscribers | Delay p50 ms | p95 ms | max ms | Server CPU % mean / max | Server RSS MiB mean / max | Generator CPU % |
|---|---|---|---|---|---|---|
| 1 | 1.73 | 2.65 | 3.39 | 9 / 13 | 199.7 / 199.9 | 6 |
| 100 | 7.64 | 10.92 | 13.32 | 39 / 56 | 245.0 / 260.5 | 44 |
| 500 | 107.16 | 178.29 | 203.12 | 91 / 103 | 349.7 / 404.8 | 113 |
| 1000 | 131.78 | 200.07 | 220.30 | 91 / 138 | 425.2 / 518.8 | 119 |

The 500 and 1000 rows are partly the load generator's: it is above 100% there, and the subscribers it
runs are one thread. The server CPU at 1000 subscribers is 91% of one core on average, which is
50,000 deliveries per second (50 updates/s times 1000), about 18 µs of server CPU per delivery (derived).
That is the order of one JSON encoding of a 2.2 KiB representation (12.42 µs median in `bench:loop`),
which fits the design below; no script isolates the encoding from the framing and the send, so this is an
inference, not a measurement. The representations here grow to the size of the bids the run has made;
their final byte size is not printed.

The cost is structural: each `Representations` subscriber is its own stream (the handler in
`packages/rpc/src/index.ts` reads `model.representations` through a sliding buffer of
`RepresentationBacklog`), the representation is the whole view and not a difference, and the server
encodes it once per subscriber [as read from the code, not isolated by a measurement].

### Memory

Server RSS and V8 heap in use, with no garbage collection forced, as one client sends bids:

| Moment | Steps sent | RSS MiB | RSS above idle MiB | Heap used MiB |
|---|---|---|---|---|
| idle after start | 0 | 198.8 | 0.0 | 50.9 |
| after 1000 steps | 1000 | 228.6 | 29.8 | 98.8 |
| after 5000 steps | 5000 | 385.7 | 186.9 | 221.5 |

During the 5 second `Present` windows RSS averages 1204.7 MiB and peaks at 2247.3 MiB with one connection
(36,724 bids sent), and peaks at 2748.0 MiB with 50. Every accepted bid grows the model's `bids` array,
and each of the 1000 retained history records holds its own copy of the model's collections, so the
memory bound is the record count times the model's size, and the model grows without limit. The
`Submit` windows, where the model stops growing at the credit limit, stay at 378.1 and 409.6 MiB mean.
The gap is listed in [TODO](../TODO.md#performance).

### Synchronisation

`Present` from one client, 2000 timed bids on a fresh set of processes per row (200 bids already in the
model), with `MUFW_SYNC`:

| Client talks to | Steps/s | p50 ms | p95 ms | p99 ms | p50 vs no sync |
|---|---|---|---|---|---|
| a server without sync | 13946 | 0.06 | 0.11 | 0.23 | 1.00× |
| the host of the log | 8383 | 0.10 | 0.18 | 0.36 | 1.73× |
| a joiner of the log | 3074 | 0.29 | 0.44 | 1.11 | 4.89× |

Sync adds 0.04 ms at the host and 0.23 ms at a joiner, on one machine over loopback. A joiner's `present`
appends to the log held by the host and returns once the entry is applied, so on a real network each
proposal at a joiner adds the round trip to the host [inference from the layer's contract in
[the SAM loop](sam-loop.md#synchronisation-across-instances); loopback hides it].

## Where the costs come from

Each cost is the price of a design choice, in the order of the sections above:

| Choice | What it buys | What it costs |
|---|---|---|
| The runtime is Effect, and every cut point is a `Schema` | typed errors and services, layers for placement, scoped fibers, parsing at the boundary | 7.1 KiB gzip for the runtime, 22.4 with schemas, 32.0 with streams and layers (the [floors](#floors)); script time at load; 0.1 µs to decode an intent and about 90 µs for a 21 KiB model |
| Every step is recorded as a history record | time travel, replay, model-based path tests, the history stream of the devtools | 218 to 8367 bytes per record; a bound on count that does not bound size |
| A representation is the whole view, not a diff | a subscriber that falls behind skips to the newest snapshot and loses nothing; no diff protocol | the whole representation is encoded and sent per update; fan-out cost grows with its size |
| One serialised writer per definition | every step atomic, in order, one permit | steps/s does not grow with connections; latency does |
| Fiber hops between an intent and the render (queue, drain fiber, forked present) | the loop is the same code in every placement | a click's result is shown one frame later under the default scheduler |
| Each `Representations` subscriber is its own stream | per-client backpressure and a bounded buffer for a stalled client | the server encodes per subscriber |
| The entry of `@mufw/core` re-exports synchronisation | one import for the package | 21.7 KiB gzip a page may never run (a gap, not a choice; see the [barrel leak](#the-barrel-leak)) |

## What this means realistically

µFW is not a performance-first framework. Its bundle, startup CPU and per-step cost are larger than a
view library's and a plain reducer's, and most of that is Effect, which it uses on purpose. What one gives
up is bytes, main-thread time at load, a frame of click latency under the default scheduler, and
per-subscriber server work. What one gets is the SAM definition as the single source of the domain, a
schema at every boundary, recorded steps, and the choice of placement per deployment without a domain
change.

Derived from the numbers above:

| Fits | Because |
|---|---|
| Forms, back-office screens, workflows, admin tools | an extra frame (about 16.7 ms at 60 Hz) is inside the 200 ms INP threshold; click to next frame is at most 45.5 ms p95 at 10× throttling; a step costs microseconds |
| Applications that load once and stay open | the 64.0 to 94.3 KiB gzip is paid once; 1.4 to 2.1 MiB of heap |
| Dashboards with some hundreds of viewers of one definition | 100 subscribers at 50 updates/s see p50 7.64 ms, p95 10.92 ms; the cost scales with updates times subscribers [inference] |
| A server with a few thousand proposals per second on one definition | `Present` over a websocket is 7305 to 10710 steps/s with a growing model, `Submit` applies 17292 to 34897 cheap steps/s |

| Does not fit without a change | Because |
|---|---|
| A page whose first-load JavaScript budget is tens of KiB | the framework floor is 42.3 KiB gzip with the barrel leak removed (probe) and 64.0 through the entry; `browser-only` is 94.3 |
| A 60 Hz animation driven through the loop | every intent adds a frame under the default scheduler and a history record per step; drive animation outside the loop [inference] |
| Thousands of live viewers of one large representation in one server process | 500 subscribers at 50 updates/s see p50 107.16 ms and 1000 see 131.78 ms, near one core of server CPU; more than one server process is not measured |
| A single definition that must apply more than about 10,000 proposals per second | the `Present` ceiling measured is 10710 steps/s; one writer does not scale with connections |
| A model that grows without bound with the default history | 1000 records each hold the model's collections: 186.9 MiB above idle after 5000 bids, and 1 to 2.5 GiB RSS in a 5 second window |
| A weak device with a strict first-interaction budget | 144.0 ms median first content for a counter and 307.2 ms for the auction at 10× throttling, compute alone; script time is 8.14× to 9.71× the baseline |

Three of the costs have a listed gap: the [barrel leak, the one-frame delay and history bounded by count
not size](../TODO.md#performance). The others are the design.
