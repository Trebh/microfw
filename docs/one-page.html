µFW

The SAM pattern on Effect 4.
Write the loop once; place it anywhere.

The problem

Front-end state machines and server workflows are written twice, with a hand-written protocol in between. Moving a rule across — a credit check, a countdown — means rewriting it, and the two halves drift.

The bet: three pillars
1SAM is the programming model.Data plus pure functions; only actions touch the world.
2Placement is a deployment decision.Browser or server is a choice of Layer, never of domain code.
3The definition is the test oracle.The pure step yields the graph; every path is replayed on the real system.
1

One loop, one effectful box

An intent becomes a proposal through an action; acceptors decide what the model becomes; state derives the representation; nap proposes what happens next. Each port on the loop stands up as a pane into the wire layer above: an RPC can cut the loop at any of the four, and the domain below never changes.

pure function effectful action data with a Schema adapter seam: a port an RPC can carry automatic intent
2

One definition, five placements

Model and actions each run in the browser or on the server, or both in a web worker. Each page picks its layers at its own composition root.

  • Zero domain changes. Moving a rule across the wire is a layer swap at the composition root plus its test.
  • Trust follows the RPC. Present applies any proposal, so only trusted clients get it. Actions in a browser or a worker ! bring a permissive credit check. Strangers get Submit, and the bidder comes from the session, never the intent.
3

Every path, replayed on the real system

The step is pure, so the control-state graph is explored offline. Each generated path runs against the system, asserting the representation at every node; the same exploration writes the definition's committed behaviour card.

A definition schemas first, then behaviour

examples/auction/src/auction/Auction.ts
export const Auction = define({
  name: "auction", model: Model, proposal: Proposal,
  intent: Intent, representation: Representation   // the cut points
})({
  initial,
  acceptors: { BidPlaced: acceptBidPlaced, … },                            // one per tag
  reactors: [], state,                                                     // pure
  nap: { opening: napOpening, open: napOpen, closing: napClosing, sold: noIntent },
  actions: { Open: …, PlaceBid: …, Tick: …, Close: … }                     // effectful
})
const Ports = makePorts(Auction)
const Loop  = layerLoopLocal(Auction, Ports)   // or the @mufw/rpc remote layers

define(schemas)(behaviour) is curried so the schemas type the behaviour's literals.

Dependencies point inward

  • @mufw/core depends on effect alone: no DOM, transport or platform.
  • Adapter packages never import each other.

Every step is recorded

  • Time travel: travelTo(seq) restores any retained record and appends a travel record; nap does not run. A history exports to JSON and replays its proposals.
  • Diagrams are derived: the Stately inspector draws state and sequence diagrams from the definition.
  • Beyond one process: the model persists through a KeyValueStore port; instances agree by applying one ordered log of proposals, and a lease picks the one that runs automatic actions.

Principles

  • Hexagonal: ports are services, adapters are layers.
  • Parse, don't validate: decode once, at the boundary.
  • Effects all the way down; run only at the edges.
  • Boring and small: a pure function over a service, a service over a feature.
  • Observable by default.
  • Honest about cost: measured against plain baselines.
Not doing
  • A general-purpose UI framework
  • Hiding Effect from its users
  • Statecharts as the source of truth
  • Winning benchmarks or the smallest bundle

How we will know it works

  • Every placement runs from one definition, with zero domain changes.
  • The same path test passes locally, over in-process RPC and against a live server.
  • Moving a rule between client and server is a one-line layer change plus its test.
